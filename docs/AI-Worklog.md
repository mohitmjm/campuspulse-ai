# AI Worklog — CampusPulse AI

**How this was built:** I wrote the brief; Claude Code (Claude Opus 5.5) built the app, plan and documents in one session. The three entries below are real decisions from that build: what the AI produced or proposed first, what was changed or rejected, and what shipped. Each final output can be checked in the linked code and tests.

---

### 1. The Copilot is a rules engine, not an LLM

- **Prompt:** "Develop a useful AI-assisted decision-support system… optionally support an external LLM… never pretend that rule-based outputs are generated by a live LLM."
- **AI output:** send campaign metrics to an LLM and let it write the recommendations — the fastest way to make the Copilot feel "AI".
- **What changed / rejected:** an LLM can misstate arithmetic (e.g. required daily pace), would need a paid key, and could not be unit-tested deterministically. The useful part of a growth copilot is *correct numbers + a clear trigger*, not prose.
- **Final output:** `lib/copilot.ts` implements 9 explicit rules (pace, channel gap, college coverage, ambassador skew, positioning, budget, late shortfall, momentum, experiment priority). Every recommendation shows its rule ID and the numbers behind it. An LLM is optional (`ANTHROPIC_API_KEY`), only rewrites the rules output, and is labelled "LLM narrative". Verified by unit tests, e.g. 160 regs on Day 4 → 340 remaining, 114/day (`tests/unit/logic.test.ts`).

### 2. Conversion rates use tracked denominators only — or show "—"

- **Prompt:** "Do not calculate conversion rates using invented denominators."
- **AI output:** show a "click-through rate" on the dashboard using the plan's assumed reach (12,000 WhatsApp members) as the denominator.
- **What changed / rejected:** reach inside WhatsApp groups is not observable; dividing real registrations by an assumed number would present a guess as a measurement.
- **Final output:** the app records anonymous session events (`page_view`, `form_start`, `form_submit`, `share_click`) and computes rates only from those (`lib/analytics.ts`). If a denominator is zero, the rate is `null` and renders "—" (tested). The dashboard states the limitation in plain text. The planning model keeps reach/CTR as clearly labelled *assumptions* on the Growth Plan page.

### 3. Tests had polluted the demo database — isolated them

- **Prompt:** "Ensure public demo visitors cannot modify real campaign records… keep demo metrics separate from real records."
- **What happened:** the first Playwright run created "Kiran T." test ambassadors in the main dev database. The AI noticed this in its own screenshot of the Ambassador page, where test records were showing up as *real* ambassadors on the leaderboard.
- **AI output:** delete the rows and move on.
- **What changed / rejected:** deleting once would not stop it happening again, and a demo that silently mixes test rows with "real" data breaks the core promise of separating simulated and real records.
- **Final output:** E2E tests now run against their own `e2e.db`, reset on every run (`playwright.config.ts`). A `scripts/clean-test-data.ts` utility removes `.test` rows, and the integration test asserts that loading or resetting a demo scenario never touches real rows.

### Other AI-assisted decisions (shorter)
- **Funnel numbers:** the AI set the three channels to come to exactly 500 (264 + 144 + 92), and a unit test fails if `lib/campaign.ts` drifts from that total or from the ₹2,000 budget.
- **Duplicate protection:** Gmail dots and `+tags` are normalized, so `p.sharma+x@gmail.com` counts as `psharma@gmail.com`. A database unique constraint also handles two submissions arriving at the same moment (tested with two parallel submits).
- **Privacy:** leaderboards show "First L." only. Real-data dashboard aggregates need an admin key (cookie). No API returns student names or emails.
